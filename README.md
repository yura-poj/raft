# Учебный Raft-кластер

Небольшая реализация каркаса Raft на Go: фиксированный кластер выбирает лидера, лидер рассылает heartbeat, а после его остановки доступное большинство проводит новые выборы. Каждый узел предоставляет REST API и встроенную страницу состояния всего кластера.

## Что реализовано

- роли `follower`, `candidate`, `leader`;
- случайный election timeout;
- `RequestVote` и один голос узла в каждом term;
- пустой `AppendEntries` как heartbeat;
- переход в follower при большем term;
- повторные выборы после остановки лидера;
- сохранение `currentTerm` и `votedFor` на диск с атомарной заменой файла;
- не более одной одновременно выполняющейся рассылки heartbeat;
- локальный и агрегированный status API;
- встроенный frontend без отдельной сборки.

Это не полная реализация Raft. Здесь нет журнала команд, репликации, state machine, snapshot и смены состава. Узел сохраняет только обязательные для leader election поля `currentTerm` и `votedFor`. Сервис предназначен для локального обучения и не должен выставляться в недоверенную сеть.

## Запуск трёх узлов

Откройте три терминала в корне проекта.

Терминал 1:

```bash
go run ./cmd/raft-node --id node1 --listen 127.0.0.1:8081 --state-file ./data/node1.json --peers node1=http://127.0.0.1:8081,node2=http://127.0.0.1:8082,node3=http://127.0.0.1:8083
```

Терминал 2:

```bash
go run ./cmd/raft-node --id node2 --listen 127.0.0.1:8082 --state-file ./data/node2.json --peers node1=http://127.0.0.1:8081,node2=http://127.0.0.1:8082,node3=http://127.0.0.1:8083
```

Терминал 3:

```bash
go run ./cmd/raft-node --id node3 --listen 127.0.0.1:8083 --state-file ./data/node3.json --peers node1=http://127.0.0.1:8081,node2=http://127.0.0.1:8082,node3=http://127.0.0.1:8083
```

Откройте [http://127.0.0.1:8081/](http://127.0.0.1:8081/). Страница любого живого узла показывает все настроенные узлы, их доступность, роль, term, известного лидера и текущий голос. Статусы собираются последовательно во времени и не являются атомарным snapshot распределённой системы.

Чтобы проверить failover, остановите терминал текущего лидера через `Ctrl+C`. Примерно после election timeout два оставшихся узла должны выбрать нового лидера, а остановленный узел будет отмечен как `unreachable`.

Флаг `--state-file` обязателен, и каждому узлу нужен отдельный файл. При перезапуске с тем же файлом узел восстанавливает term и голос. Удаление файла сбрасывает это состояние и допустимо только при намеренном создании нового учебного кластера.

## REST API

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/health` | Liveness процесса |
| `GET` | `/status` | Состояние текущего узла |
| `GET` | `/cluster/status` | Состояние всех настроенных узлов |
| `POST` | `/raft/request-vote` | Внутренний запрос голоса |
| `POST` | `/raft/append-entries` | Внутренний heartbeat |
| `GET` | `/` | Веб-интерфейс |

Примеры:

```bash
curl http://127.0.0.1:8081/status
curl http://127.0.0.1:8081/cluster/status
curl http://127.0.0.1:8081/health
```

Внутренние RPC сохраняют стандартные поля Raft, но в этой версии поддерживают только пустой журнал: `last_log_index`, `last_log_term`, `prev_log_index`, `prev_log_term` и `leader_commit` должны быть равны `0`, а `entries` должен отсутствовать, быть `null` или пустым массивом.

## Настройки времени

Значения по умолчанию:

- heartbeat: `100ms`;
- election timeout: случайно от `300ms` до `600ms`;
- timeout одного peer RPC: `150ms`.

Их можно изменить флагами `--heartbeat`, `--election-min`, `--election-max`, `--rpc-timeout`. Должно выполняться `heartbeat < election-min < election-max`.
